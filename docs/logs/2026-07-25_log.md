## 遇到的风控

| 风控手段 | 表现 |
|---------|------|
| 环境指纹校验 | 程序驱动的浏览器里，滑块验证无论怎么滑都显示「验证失败」——能识别鼠标轨迹来源是不是程序注入 |
| JS 挑战页 | view-source 只能看到挑战脚本，真页面要 JS 跑完挑战才渲染 |
| 高频访问风控 | 每爬 60 条左右必触发一次验证页，通行凭证过期 |
| 请求级拦截 | requests 直接请求详情页，只返回风控壳子页面，正文完全不在 |

## 尝试过的方案和失败记录

| 方案 | 结果 | 失败原因 |
|------|------|---------|
| requests + Cookie 直接请求 | 失败 | Cookie 含中文导致编码报错；修复后拿到的是风控壳子页面 |
| Selenium 新开浏览器页面内请求 | 失败 | 第一条就被拦，弹假验证页 |
| Selenium 新开浏览器直接访问 | 失败 | 弹滑块验证，且滑了永远失败（环境指纹被识别） |
| 复用日常浏览器用户数据 | 失败 | 新版浏览器 profile 结构兼容性差，起不来 |
| CDP 接管日常浏览器 | 部分成功 | 能接管，但还是会触发验证，且程序环境里滑块永远失败 |
| 模拟真人路径（先搜索页再跳详情页） | 失败 | 不认跳转轨迹，照样拦 |
| 换手机热点刷新 IP | 失败 | 不是 IP 的事，是浏览器指纹和行为模式的事 |

## 最终方案：人机协同，程序接力

**核心发现**：滑块校验的是「这个会话是不是真人控制的」。程序驱动的会话里滑块，轨迹来源被识别为注入，永远判失败；但验证通过后写入的通行凭证是会话级的，不区分人和程序。

**方案**：以调试模式启动独立的浏览器环境 → 人工完成一次滑块验证（真人轨迹，能通过）→ 程序通过 CDP 接管同一个浏览器会话批量抓取 → 通行凭证过期触发验证时，人工再介入一次，程序继续。

**关键细节**：
- 浏览器驱动版本必须和浏览器完全一致（版本不匹配会在接管模式下无限卡住）
- 结尾不要 `driver.quit()`，浏览器是人工环境的，跑完不会被关

## 解析逻辑（兼容两种详情页模板）

1. **方案1（优先）**：直接找标准正文容器 `div.bmsg.job_msg.inbox`（大厂雇主页用）
2. **方案2**：找 `h2.prop` 标题「职位描述」，取后面的兄弟区块
3. **方案3 兜底**：找含「岗位职责」「工作职责」「职位描述：」关键词的最小 div（100-3000 字）

**拆分逻辑**：找到「任职要求：」「任职资格：」「岗位要求：」「职位要求：」任一分隔词，前半段存职位描述，后半段存任职要求。

**福利标签**：从 `div.tags` 提取所有 span/a/em/i 文本。

## 落盘逻辑缺陷（今日最大教训）

**问题**：flush 逻辑是「每 20 条把内存里全部数据覆盖写一次 CSV」，程序中断时，最后一次 flush 之后跑的所有数据都在内存里丢失。

**结果**：实际爬了 1213 条，但只落盘 100 条，丢了 1112 条。断点文件 `detail_crawled.txt` 里记了 1213 条（还有重复），但 CSV 里只有 100 条有详情数据。

**修复**：改成每条都落盘（`job.update(detail)` 后立即 flush），中断只丢当前一条。代价是每条多 0.1 秒写盘时间，但比丢 1000 条强太多。

**教训**：批量任务落盘策略要「宁滥勿缺」，内存缓存是性能优化，不是可靠性方案。

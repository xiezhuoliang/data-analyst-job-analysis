## 遇到的反爬

| 反爬手段 | 表现 |
|---------|------|
| 阿里云 WAF 环境指纹校验 | Selenium 驱动浏览器里，滑块验证无论怎么滑都显示「验证失败，请刷新」——WAF 能识别鼠标轨迹来源是不是程序注入 |
| JS 挑战页 | view-source 只能看到一行 textarea + aliyun_waf_aa 脚本，真页面要 JS 跑完挑战才渲染 |
| 高频访问风控 | 每爬 60 条左右必触发一次验证页，通行证 Cookie 过期 |
| 请求级拦截 | requests 直接请求详情页，返回 98KB 的风控壳子页面，正文完全不在 |

## 尝试过的方案和失败记录

| 方案 | 结果 | 失败原因 |
|------|------|---------|
| requests + Cookie 直接请求 | 失败 | Cookie 含中文导致 latin-1 编码报错；修复后拿到的是 WAF 壳子页面 |
| Selenium 新开浏览器 fetch 详情页 | 失败 | 第一条就被 WAF 拦，弹假验证页 |
| Selenium 新开浏览器 driver.get | 失败 | 弹滑块验证，且滑了永远失败（环境指纹被识别） |
| 复用日常 Edge 用户数据（--user-data-dir） | 失败 | Edge 150 的 profile 结构兼容性差，浏览器起不来 |
| CDP 接管日常 Edge（9222 端口） | 部分成功 | 能接管，但还是会触发验证，且程序环境里滑块永远失败 |
| 模拟真人路径（先搜索页再跳详情页） | 失败 | WAF 不认跳转轨迹，照样拦 |
| 换手机热点刷新 IP | 失败 | 不是 IP 的事，是浏览器指纹和行为模式的事 |

## 最终成功的方案：人肉开门，程序接力

**核心发现**：WAF 的滑块校验的是「这个会话是不是真人控制的」。Selenium 驱动的会话里滑块，轨迹来源被识别为程序注入，永远判失败。但验证通过后写的通行 Cookie 是会话级的，不区分人和程序。

**操作流程**：
1. 杀干净所有 Edge 进程（`taskkill /f /im msedge.exe`）
2. cmd 里用调试模式启动日常 Edge：`"C:\\Program Files (x86)\\Microsoft\\Edge\\Application\\msedge.exe" --remote-debugging-port=9222 --user-data-dir="C:\\edge_debug_profile"`
3. 在这个调试 Edge 里手动打开一个详情链接 → 手动滑过验证（真人轨迹，能通过）→ 看到正常详情页
4. 马上跑程序（Selenium 通过 `debuggerAddress: 127.0.0.1:9222` 接管同一个浏览器会话）
5. 程序拿着通行证 Cookie 批量跑，每 60 条左右通行证过期再弹验证 → 手动再滑一次 → 程序继续

**关键细节**：
- msedgedriver 版本必须和浏览器完全一致（147 驱动配 150 浏览器会在 CDP 模式下无限卡住）
- 验证调试端口是否生效：浏览器里打开 `http://localhost:9222/json`，能看到 JSON 才是真的起来了
- 结尾不要 `driver.quit()`，浏览器是你自己的，跑完不会被关

## 落盘逻辑缺陷（今日最大教训）

**问题**：flush 逻辑是「每 20 条把内存里全部数据覆盖写一次 CSV」，程序中断时，最后一次 flush 之后跑的所有数据都在内存里丢失。

**结果**：实际爬了 1213 条，但只落盘 100 条，丢了 1112 条。断点文件 `detail_crawled.txt` 里记了 1213 条（还有重复），但 CSV 里只有 100 条有详情数据。

**修复**：改成每条都落盘（`job.update(detail)` 后立即 flush），中断只丢当前一条。代价是每条多 0.1 秒写盘时间，但比丢 1000 条强太多。

**教训**：批量任务落盘策略要「宁滥勿缺」，内存缓存是性能优化，不是可靠性方案。
